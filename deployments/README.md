# Развёрнутые адреса

Справочный перечень. **Источник истины — объект в бэкенде** (`Property.TokenContractAddress`,
`Property.TokenChain`, `Property.IssuerWalletAddress`, заполняются через `Property.SetTokenContract`).
Адреса контрактов не хранятся в конфигурации приложения.

Одна сеть на один выпуск: у каждого объекта ровно один контракт токена и ровно один адрес.
**Сейчас это правило нарушено** — под ATRP-BR1 развёрнуты два контракта, см. ниже.

### ATRP-BR1 — два контракта на один объект, требуется решение

Под объектом `b6c59d6c-3b03-495c-a34f-f73cabb9d488` развёрнуты **два** контракта: 24 августа и
3 сентября 2026. У них совпадают `symbol`, `PROPERTY_ID`, `maxSupply`, `decimals` и раскладка ролей —
различить их по состоянию контракта нельзя, только по адресу. **На обоих уже выпущены доли.**

| Параметр | 24 августа | 3 сентября |
|---|---|---|
| Адрес | `0x440bc3b478d6d5c18ec537431e7C3e602E46c088` | `0x263a28a498c35e9396a171cf11aafb9fa9a04c78` |
| Блок развёртывания | 126 927 728 | 128 823 353 |
| Выпущено | **100** | **8** |
| `maxSupply` | 72 600 | 72 600 |
| `decimals` | 0 — доля неделима | 0 |
| Приостановлен | нет | нет |
| `PROPERTY_ID` | `0xb6c59d6c3b03495ca34ff73cabb9d488…` | то же самое |
| Allowlist | `0x5f1586bDaCD7bbD6da2E8EB377C51A268afd40D2` | тот же |

Стоимость объекта 7 260 000 KGS, доля 100 KGS, минимальная покупка 100 долей.

Значения выше сверены с сетью 7 сентября 2026 (`totalSupply`, `maxSupply`, `decimals`, `paused`,
`propertyId`, `allowlist`, `hasRole` по каждой роли). Allowlist и IdentityRegistry переиспользованы
обоими контрактами, заново не разворачивались; `agents()` подтверждает агента белого списка `true`.

Что нужно сделать отдельной задачей: сверить `Property.TokenContractAddress` в бэкенде с этими двумя
адресами, назвать действующий контракт и пометить второй устаревшим — как это сделано для ATRP-T1.
Пока обе записи равноправны, реестр держателей объекта разложен по двум контрактам, и суммарный
выпуск объекта равен 108 долям, а не 100.

**Не восстановлено: адреса получателей и хеши транзакций белого списка и минта.** Оба выпуска
(24 августа и 3 сентября) старше окна хранения публичных узлов BNB testnet — `eth_getLogs` и
исторические вызовы состояния отвечают `history has been pruned`, архивного состояния публичные RPC
не отдают, ключа BscScan нет (по той же причине не верифицированы исходники). Взять эти данные можно
только из бэкенда: `Investment.TransactionHash` и `Investment.WalletAddress` по объекту, плюс
`WhitelistEntry`. Дописать сюда после выгрузки из БД.

Косвенная проверка, которую сделать удалось: на обоих контрактах баланс равен нулю у всех служебных
адресов — `DEFAULT_ADMIN`, `MINTER`, `COMPLIANCE`, `PAUSER`, `ORACLE`, агент белого списка и
развёртыватель. Значит, все 108 долей ушли на адреса инвесторов и ни одна не осела на служебном ключе.

### ATRP-T1 — устарел, для прогона непригоден

Оставлен в перечне как история. Две причины непригодности:

`PROPERTY_ID` — заглушка `0x…01`, то есть контракт не называет никакого выпуска. Привязать его к
объекту нельзя: бэкенд сверяет `propertyId()` с `Property.Id` и вернёт 409. Значение неизменяемо,
поэтому и потребовался новый контракт; скрипт развёртывания заглушку больше не пропускает.

`maxSupply = 1 000 000`. Прежнее замечание в этом файле утверждало, что `decimals = 0` — это
сборка «до перехода на `decimals = 2`» и потому минт 10 долей выпустил бы 1000. Замечание
устарело: переход на дробные доли отменён, `TokenAmount.Scale` вернулся к 0, и `decimals = 0`
теперь верное значение — оно же у обоих контрактов ATRP-BR1.
