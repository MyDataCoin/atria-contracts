# Инварианты контракта

Это утверждения, которые обязаны выполняться после **любой** последовательности законных действий —
в любом порядке, любыми ролями. Юнит-тесты показывают, что каждая функция ведёт себя правильно на
случаях, которые кто-то придумал. Инварианты отвечают на другой вопрос: можно ли вообще завести
контракт в противоречивое состояние. Именно это и проверяет аудитор.

Проверяются машинно: [`test/AtriaPropertyTokenInvariants.t.sol`](../test/AtriaPropertyTokenInvariants.t.sol),
256 прогонов по 500 вызовов каждый — 128 000 вызовов на инвариант.

```
forge test --match-path "test/AtriaPropertyTokenInvariants.t.sol"
```

## Список

| Инвариант | Почему он важен |
|---|---|
| `totalSupply() <= maxSupply()` | Единственное число, под которое написана государственная регистрация выпуска. Превышение означает, что реестр и цепочка описывают разные выпуски. |
| `totalSupply() == выпущено − сожжено` | Ловит любой путь, который создаёт или уничтожает доли без учёта. |
| `Σ balanceOf(держатели) == totalSupply()` | Каждая существующая доля лежит ровно на одном адресе. Доля, не принадлежащая никому, — это доля, по которой реестр не сможет выплатить дивиденд. |
| `maxSupply()` только уменьшается и никогда ниже `totalSupply()` | Потолок, который может расти, делает зарегистрированный объём бессмысленным; потолок ниже выпущенного оставил бы существующих держателей вне лимита. |
| `decimals() == 2` | Доля делится до одной сотой, и ровно с этим масштабом её хранит реестр (`TokenAmount.Scale`). Расхождение означало бы, что реестр и цепочка описывают разные величины владения. |
| `propertyId()` неизменяем и не равен нулю | Контракт называет выпуск, который представляет. Без этого токен — анонимный ERC-20, о котором бэкенд лишь утверждает, что он относится к объекту, и неверно записанный адрес неотличим от верного. |
| Контракт и нулевой адрес не держат долей | Доли, «застрявшие» на самом контракте, не принадлежат никому и не выплачиваются. |

## Что инварианты сознательно не проверяют

**Утечка флага `_complianceOverride`.** Покрыта прямым тестом
`test_restrictionsRestoredAfterComplianceAction`, который может проверить конкретную ошибку возврата.
Инвариант этого не может: он не должен менять состояние, которое сам же проверяет, а для проверки
ограничения нужно попытаться его нарушить.

**Разделение ролей.** Это свойство контроля доступа, а не состояния: проверяется юнит-тестами
(`test_minterCannotBurnFreezeOrPause` и соседние) и раскладкой прав в `CheckDeployment`.

**Достоверность данных об обеспечении.** Контракт записывает то, что засвидетельствовал оракул, и не
проверяет это — доверие вынесено за пределы контракта осознанно.

## Как читать handler

Фаззер водит контракт через `TokenHandler`, который вызывает функции так, как это может сделать
реальный ключ: минтит только минтер, жжёт и замораживает только комплаенс, держатели берутся из
фиксированного набора, чтобы балансы действительно пересекались. Handler без этих ограничений
потратил бы прогон на возвраты по контролю доступа и не доказал бы ничего.

Возвраты в отчёте (порядка 180 на 128 000 вызовов) — это пути, где действие законно, но состояние
его не допускает: перевод от замороженного адреса, сжигание с нулевого баланса. Это ожидаемо.
